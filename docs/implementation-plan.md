# サウンドマネージャー実装計画

作成日: 2026-09-06

## 目的と前提

[基本仕様](sound-manager-spec.md)に基づき、TypeScript製HTML5ゲーム向けのHowler.jsサウンドマネージャーを実装する。Cursor Grok4.6を進行管理役、Cursor Compose2.5を実装役のサブエージェントとして運用する。

モデル名称はユーザー指定の表記を使用している。本書は役割と作業手順の計画であり、Cursorのモデル選択・サブエージェント設定を実行または検証した記録ではない。開始時に利用環境の実際のモデル名と委譲機能を確認し、利用できない場合は代替モデルへ無断変更せず状況を報告する。

現時点では仕様書とREADMEのみがあり、実装・ビルド設定・テストは未作成。全工程を未着手として開始する。初版の範囲は5区分の再生、再生ハンドル、JSONカタログ、グループ単位のプリロード・解放、ブラウザーで動作確認できるデモとする。将来のBGM多チャンネル同時再生は拡張可能な構造までとし、初版で機能を追加するかは別途判断する。

## 実装完了後の位置づけ

上記は計画作成時点の記録である。P0〜P8 の実装と自動検証、および Chromium 系でのデモ操作確認は完了した。スピーカーによる実音の聴取と Safari / Firefox / 実機モバイルブラウザーは未検証であり、公開・push・パッケージ配信は引き続き本計画の対象外である。

## 役割分担

| 担当 | 責任 | 成果物 |
| --- | --- | --- |
| ユーザー | ゲーム側の要求、操作感や互換性を変える未確定仕様の判断 | 仕様判断 |
| Grok4.6：進行管理 | 仕様整理、依存関係と作業範囲の管理、実装指示、差分レビュー、検証結果の確認、完了判定 | 決定記録、タスク指示、進捗記録、レビュー結果 |
| Compose2.5：実装サブエージェント | 指示された範囲の設計・実装・テスト・修正、問題の報告 | コード、テスト、利用例、実行結果と残課題 |

Grok4.6は原則として進行管理とレビューを担当し、実装変更はCompose2.5へ委譲する。Compose2.5は未確定のゲーム挙動を独断で確定せず、必要な判断と推奨案を返す。ファイル分割、内部命名、テスト用の補助実装など、外部仕様を変えない通常の実装判断は担当者が進める。

初期運用は実装サブエージェント1体で工程ごとに進め、同じファイルへの並行編集を避ける。追加の並列化が必要になった場合は、Grok4.6が担当ファイルと依存関係を分離してから割り当てる。

## 仕様判断と記録

基本仕様の「確定事項」を実装の根拠とする。「提案・未確定事項」は、その工程に必要な部分を解決してから依存する実装へ進む。すべての未確定事項が決まるまで全作業を停止する必要はない。

Grok4.6はゲーム側から見える選択について、推奨案・代替案・影響を整理してユーザーの判断を得る。採用済みの指示は再確認せず、基本仕様へ反映する。通常の内部設計判断はGrok4.6が決定し、理由を記録する。

開始時に `docs/implementation-progress.md` を作成し、タスクID、状態、担当、依存、変更箇所、検証結果、未解決事項を記録する。状態は `未着手 → 実装中 → レビュー中 → 完了` とし、判断待ちの場合は対象と理由を併記する。仕様判断も同ファイルに判断ID・決定内容・根拠・関連タスクを記録し、確定した外部仕様は基本仕様にも反映する。

## 推奨する内部構成

以下は実装の出発点であり、公開仕様を維持した内部構成の改善は可能とする。

| 構成要素 | 責任 |
| --- | --- |
| SoundManager | 公開API、初期化、各管理機能への委譲 |
| Catalog | JSON検証、IDとURL、グループ定義の登録 |
| ResourceStore | 読み込み状態・処理の共有、グループと再生による保持、解放 |
| AudioBackend / HowlerBackend | Howler.js操作とイベントの変換。テスト時は制御可能な代替実装を使用 |
| PlaybackRegistry | 再生要求の識別、ハンドル状態、終了処理 |
| ChannelPool | 区分ごとの枠数、割り当て、解放、競合処理 |
| 各区分の制御 | BGMのクロスフェード、BGSの指定再生、ME・SE・SYSTEM SE固有の規則 |

音源ID、公開再生ハンドル、Howler内部の再生ID、チャンネル番号は区別する。Howler側の内部プール設定を、そのまま本ライブラリの同時再生数として扱わない。Howler.jsの仕様と採用バージョンは実装時に公式資料で確認する。

同じ音源から複数の再生が発生しても、音量・パン・停止などが意図せず他の再生へ波及しないようにする。BGMの枠は配列や共通プールで管理し、固定のA/B専用設計に閉じない。

基本順序はP0からP8。依存しない調査や判断整理は並行してよい。公開・push・パッケージ配信は本計画の実装完了条件に含めない。コミットやPRを作成する場合の文章は日本語とする。

## 検証方針

時間とイベントを制御できるバックエンド代替実装で競合・状態遷移を検証し、実際のHowler.jsとブラウザーによる検証も行う。モックの成功だけで実際に音が鳴ることを確認済みとしない。

| 対象 | 必須の確認 |
| --- | --- |
| カタログ | 登録のみでは音源ロードなし。不正形式・未知IDは決定したエラー規則に従う |
| プリロード | 全件成功・部分失敗・再試行。同一IDへの同時要求を共有し、Promiseが未解決で残らない |
| 解放 | 2グループ共有音源を片側の解放で破棄しない。再生中の音源を保護し、最後の利用終了後は決定した規則で回収する |
| 非同期競合 | ロード中の解放、停止後の遅延イベント、チャンネル再利用を検証する。自動ロード採用時は停止後に発音しない |
| ハンドル | 全区分の個別停止、終了後の操作、古いハンドルから新しい音への誤操作防止 |
| SE・SYSTEM SE | 通常SE16枠とSYSTEM SE4枠を独立管理し、終了時に枠が戻る。満杯時は決定した仕様に従う |
| BGS | 4音同時再生、指定枠の置き換え、番号指定とハンドル指定の停止 |
| BGM | クロスフェード、途中停止、連続切り替え、初期位置、決定済みループ仕様 |
| ME | 1枠で最新要求へ置き換え、複数同時再生、採用したBGM連動の終了・停止・失敗時動作 |
| ブラウザー | 初回操作による再生許可、実際の発音、パン・音量・フェード。検証ブラウザーと未検証環境を記録する |

デモ用音源は利用・再配布可能なものに限定し、出典または生成方法を記録する。ビルド・型検査・対象テストを各工程で実施し、最後に統合検証を行う。

## 委譲とレビューの進め方

1. Grok4.6が対象工程の依存と仕様判断を確認する。
2. Grok4.6が下記テンプレートでCompose2.5に1つのまとまったタスクを渡す。
3. Compose2.5が実装・対象検証を行い、変更と結果を返す。
4. Grok4.6が実際の差分・検証結果を確認する。不足があれば同じタスクとして修正を依頼する。
5. 受け入れ条件を満たしたら進捗記録を更新し、次の工程へ進む。

## 初版の完了判定

- 基本仕様の確定事項が実装・利用例・検証に対応している。
- 各区分の同時再生数と全区分のハンドル指定停止が動作する。
- カタログ登録、グループプリロード、共有、解放が一連の操作として動作する。
- 実装に必要だった未確定事項が解決され、仕様書へ反映されている。
- ビルド・型検査・必須テストが成功し、実ブラウザーの確認結果が記録されている。
- READMEから導入方法、API例、仕様、制約、デモの実行方法に到達できる。
- 残っている将来拡張と未検証事項を明示し、実装済み機能と混同しない。
